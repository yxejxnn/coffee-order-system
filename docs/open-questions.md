# 열린 질문 / 미결정 사항 (open-questions)

**Clarify 단계의 산출물.** 정책·요구사항이 확정되지 않아 **추측하면 안 되는** 지점을 여기에 모은다.

> 하네스의 핵심 규칙: **애매하면 추측하지 말고 멈춘다.** 그 "멈춘 지점"이 이 문서다.
> 여기 쌓인 질문은 답이 정해지면 → 구조적 결정이면 `docs/adr/`로 승격, 단순 확인이면 해당 `design.md`/정책에 반영하고 닫는다.

## 표

발제가 요구사항을 일부러 열어둔 부분들. 사용자와 1차 확정한 잠정값을 적었다.

| 상태 | 질문 | 현재 결정(잠정) | 반영한 곳 |
| --- | --- | --- | --- |
| Resolved | 회원가입 API가 필요한가? | 불필요. 회원은 시드 데이터로 존재, 식별값=`member.id` | `db/member.md` |
| Resolved | 포인트 충전 상한/한도가 있는가? | 없음. 양수만 검증(최소 정책) | `policy/point.md` |
| Resolved | 주문내역 실시간 전송 방식은? | Kafka 비동기(커밋 후 발행) | `adr/ADR-002` |
| Resolved | 인기 메뉴 집계 저장소는? | Redis ZSET(일자 버킷), 원천은 `ORDERS` | `adr/ADR-003` |
| Resolved | "최근 7일" 기준은? | 조회 시점 당일 포함 7개 일자 버킷 합(롤링) | `policy/popular-menu.md` |
| Resolved | "주문 횟수" = 건수인가 수량인가? | 주문 **건수**(발생 횟수)로 해석 | `policy/popular-menu.md` |
| Resolved | 인기 메뉴 동점 처리 기준은? | 횟수 desc → `menuId` asc | `policy/popular-menu.md` |
| Resolved | 메뉴 재고 개념이 있는가? | 없음(무제한 판매) | `db/menu.md` |
| Open | 데이터 수집 플랫폼 전송 실패 시 정책(재시도 횟수/보관)? | N회 재시도 후 로그(Outbox 미도입) — 확인 필요 | `adr/ADR-002` |
| Open | 주문 취소/환불 요구가 있는가? | 범위 밖으로 가정 — 확인 필요 | (해당 시 신규 ADR) |

> Resolved 항목은 이후 다른 방향이 확인되면 해당 문서/ADR을 갱신한다. Open 항목은 확인되는 대로 반영한다.

## 상태 값

- `Open` — 아직 결정 안 됨. 이 항목에 걸린 구현은 진행하지 않는다(또는 잠정값임을 명시).
- `Resolved` — 결정됨. "반영할 곳"에 옮기고 링크를 남긴 뒤 닫는다.

## 워크플로우 연결

- **Clarify**: 계획 중 정책 공백을 만나면 planner가 여기에 질문을 추가하고 멈춘다(추측 금지).
- **휴먼 게이트**: 사용자가 답하거나 "잠정값으로 진행"을 승인한다.
- 결정이 구조적이면 `docs/adr/`로 승격한다.
