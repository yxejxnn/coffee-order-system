# ADR-004 데이터 모델 — 포인트 분리 & order_group_id (ORDER_ITEM 없음)

## 상태와 결정일
Accepted. 결정일: 2026-07-14.

## 맥락과 문제
동시성·일관성을 만족하는 최소 데이터 모델을 정한다. 두 가지 설계 선택이 있다.
1. 포인트 잔액을 `MEMBER`에 컬럼으로 둘 것인가, 별도 `POINT` 테이블로 분리할 것인가.
2. 주문을 `ORDER` 헤더 + `ORDER_ITEM` 상세로 둘 것인가, 단일 테이블로 둘 것인가.

## 결정 동인
- 동시성 제어(비관적 락)의 **범위 최소화**. → [ADR-001](ADR-001-포인트-동시성제어.md)
- 발제 API 범위(메뉴 1건 주문, 주문 상세 조회 API 없음)에 맞는 **과하지 않은 모델**.

## 검토한 선택지 · 결정

**(1) 포인트: `POINT` 테이블 분리 — 채택**
| 선택지 | 락 범위 | 판단 |
| --- | --- | --- |
| `MEMBER.balance` 컬럼 | 회원 row 전체 잠금(이름 등 무관 필드까지) | 제외 |
| **`POINT`(1:1) 분리** | 잔액 행만 잠금 | **채택** |
→ 충전/차감 락이 잔액 행에만 걸려 경합 범위가 최소화된다.

**FK 방향: `POINT`가 `MEMBER`를 참조(그 반대가 아님)**
1:1 관계에서는 한쪽이 FK를 가져야 한다. `MEMBER`가 아니라 `POINT`가 `member_id`를 갖는 이유:
- **생성 시점이 다르다** — `MEMBER`는 시드로 항상 존재하지만, `POINT`는 해당 회원이 **처음 충전할 때 lazy 생성**된다(회원가입 API 없음, → [open-questions](../open-questions.md)). 반대로 `MEMBER`가 `point_id`를 가지면, 첫 충전 전까지 그 컬럼이 계속 NULL이어야 해서 "항상 존재하는 핵심 엔티티"가 "아직 없을 수도 있는 부가 상태"에 오염된다. 지금 구조에서 `MEMBER`는 포인트를 전혀 모르고(`db/member.md`에 포인트 관련 컬럼 없음), `POINT`만 자신이 누구 것인지 안다 — 의존 방향이 "부가 정보 → 핵심 엔티티"로 향한다.
- **조회·락 패턴이 항상 "회원 → 포인트" 방향** — 충전/차감은 항상 `SELECT ... FROM POINT WHERE member_id = ? FOR UPDATE`로 시작한다(→ [ADR-001](ADR-001-포인트-동시성제어.md)). `uk_member_id` 유니크 인덱스로 바로 히트된다. 반대 방향이면 `MEMBER`를 먼저 조회해 `point_id`를 얻고 다시 `POINT`를 조회하는 홉이 하나 더 생긴다.

**(2) 주문: `ORDER_ITEM` 없이 단일 `ORDERS` + `order_group_id` — 채택**
| 선택지 | 적합성 | 판단 |
| --- | --- | --- |
| `ORDER` 헤더 + `ORDER_ITEM` | 다건 카트엔 정석, 그러나 현재 API는 메뉴 1건·상세조회 없음 → 과설계 | 제외 |
| **단일 `ORDERS` + `order_group_id`(UUID)** | 1건 주문에 충분, `order_group_id`가 결제·이벤트·멱등 키 겸용 | **채택** |
→ 다건 확장 시 같은 `order_group_id`로 여러 행을 묶으면 되어 확장 여지도 남긴다.

## 결정과 이유
- `POINT`를 1:1로 분리해 락 범위를 잔액 행으로 좁힌다.
- `ORDER_ITEM`을 만들지 않고 `ORDERS` 1행 = 주문 1건. `order_group_id`(UUID)가 결제 단위·Kafka 멱등 키·재조회 키를 겸한다.
- `unit_price` 스냅샷으로 가격 변경이 과거 주문에 영향 없게 한다.

## 결과와 단점
- 얻는 것: 최소 락 범위, 발제 범위에 딱 맞는 단순 모델, 확장 여지(`order_group_id` 그룹핑).
- 비용: `POINT` 분리로 조인 1회 추가. 다건 주문 요구가 생기면 `ORDERS` 사용 패턴을 재검토해야 함(단, 스키마 변경은 최소).

## 검증 현황과 계획
- Level 2~4: 엔티티/스키마와 문서 일치 확인, 주문·차감·이력이 한 트랜잭션에서 정합하게 반영되는지 테스트.

## 재검토 조건
- 주문 상세 조회 API나 진짜 다건 카트가 요구되면 → `ORDER_ITEM` 도입 재검토.
