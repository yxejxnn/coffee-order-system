# ADR-001 포인트 잔액 동시성 제어 — 비관적 락

## 상태와 결정일
Accepted. 결정일: 2026-07-14.

## 맥락과 문제
포인트 충전·주문 결제는 모두 `POINT.balance`를 읽고 갱신한다. 다음이 동시에 일어날 수 있다.
- 같은 회원이 **동시에 여러 번 주문**(따닥 클릭) → 잔액보다 많이 차감(oversell)되면 안 됨.
- 충전과 주문이 동시 → lost update로 잔액이 어긋나면 안 됨.
- 발제의 도전 요구: 앱이 **다수 인스턴스**로 떠도 정합성 유지.

핵심 관찰: 모든 인스턴스가 **하나의 MySQL을 공유**한다. 즉 "멀티 인스턴스 일관성" 문제는 사실상 "**하나의 DB 행에 대한 동시 접근**" 문제로 환원된다.

## 결정 동인
- 잔액은 돈이므로 **정합성 최우선**(oversell 절대 불가).
- 동일 회원 반복 요청이 현실적 → 충돌 빈도가 낮지 않다.
- 인프라 추가 비용은 정당화될 때만.

## 검토한 선택지

| 선택지 | 충돌 시 동작 | 정합성 | 운영 위험 | 판단 |
| --- | --- | --- | --- | --- |
| **비관적 락 (`SELECT … FOR UPDATE`)** | 대기 후 순차 처리 | 강함 | 락 대기·데드락 관리 필요(행 단위라 범위 작음) | **채택** |
| 낙관적 락 (version) | 충돌 시 예외→재시도 | 강하나 재시도 로직 필요 | 동일 회원 반복 요청에서 **재시도 폭주** 위험 | 제외 |
| 분산 락 (Redisson) | 앱 레벨 락으로 직렬화 | 강함 | Redis 의존·락 누수/TTL 관리, **DB 락으로 충분한데 중복** | 제외(보류) |

## 결정과 이유
`POINT` 행에 **비관적 락**(`@Lock(PESSIMISTIC_WRITE)` / `SELECT … FOR UPDATE`)을 걸어 충전·차감을 직렬화한다.
- 공유 MySQL 한 대이므로 DB 락만으로 멀티 인스턴스 정합성이 성립한다 → **분산 락 불필요**.
- 낙관적 락은 동일 회원 반복 요청에서 재시도 스톰 위험이 있어 제외.
- 락 범위를 좁히려 `POINT`를 `MEMBER`에서 분리했다. → [ADR-004](ADR-004-데이터모델-포인트분리.md)

## 결과와 단점
- 얻는 것: oversell/lost update 원천 차단, 구현·설명 단순.
- 비용: 같은 회원 요청은 직렬화되어 처리량 제한(회원 단위라 전체 병목은 아님). 데드락 방지를 위해 **락 획득 순서 고정**(항상 `POINT` 먼저) 필요.

## 검증 현황과 계획
- Level 4~5: 동시 주문 N스레드 테스트로 최종 잔액·주문 수가 정확한지 검증(초과 차감 0). 동시 충전 테스트로 lost update 없음 검증.

## 재검토 조건
- DB가 여러 개로 샤딩되거나, 포인트 트래픽이 단일 행 락으로 감당 안 될 때 → 분산 락/큐 직렬화 재검토.
