# ADR-003 인기 메뉴 집계 전략 — Redis ZSET(일자 버킷) + 멱등

## 상태와 결정일
Accepted. 결정일: 2026-07-14.

## 맥락과 문제
최근 7일 인기 메뉴 3개를 조회한다(발제 4). 조건:
- **카운트가 정확해야** 한다.
- 앱이 **다수 인스턴스**로 떠도 합산이 맞아야 한다.
- 조회는 사용자 대면이므로 빨라야 한다.

집계 소스로 Kafka `OrderCompletedEvent`를 소비한다(at-least-once → **중복 전달 가능**). → [ADR-002](ADR-002-주문이벤트-비동기전달.md)

## 결정 동인
- 조회 지연 최소화, 멀티 인스턴스에서 합산 일관.
- at-least-once 하에서도 **중복 없는 정확 카운트**.
- 원천 데이터 보존(재구축 가능성).

## 검토한 선택지

| 선택지 | 조회 성능 | 멀티 인스턴스 합산 | 정확성 | 판단 |
| --- | --- | --- | --- | --- |
| **Redis ZSET(일자 버킷) + 멱등 SET** | 빠름(ZSET union) | Redis 원자 연산으로 일관 | 멱등으로 정확 | **채택** |
| DB 집계 쿼리(`COUNT+GROUP BY`) | 느려질 수 있음(스캔) | 자연히 일관 | 정확 | 보류(재구축·검증용으로만) |
| 앱 메모리 집계 | 빠름 | **인스턴스별로 갈림(불일치)** | 취약 | 제외 |

## 결정과 이유
- 소비자가 **일자별 Redis ZSET** `menu:ranking:{yyyy-MM-dd}`의 멤버(menuId) 점수를 `ZINCRBY`로 올린다. 조회는 최근 7개 일자 키를 **union**해 상위 3개를 읽는다.
- **멱등**: 증가 전 `order_group_id`를 Redis SET(처리 완료 표식)에 넣고, 이미 있으면 skip → Kafka 재전송 중복 집계 차단. `ZINCRBY`는 원자적이라 멀티 인스턴스 동시 증가도 안전.
- **원천은 `ORDERS`**: Redis는 fast path. Redis 유실 시 `ORDERS`(`created_at`, `menu_id` 인덱스)로 재구축한다. DB 집계 쿼리는 이 재구축·검증 경로로만 사용.
- 일자 버킷이라 **7일 롤링 윈도우**를 키 union으로 자연히 구현하고, 만료도 키 TTL로 단순.

## 결과와 단점
- 얻는 것: 빠른 조회, 멀티 인스턴스 일관, 중복 없는 정확 카운트, 재구축 가능.
- 비용: Redis-DB 이중 저장(원천/캐시 역할 분리로 관리), 멱등 SET 저장 공간(TTL로 관리).

## 검증 현황과 계획
- Level 4~5: 같은 `order_group_id` 이벤트 2회 전달 시 카운트 1만 증가(멱등) 검증. 7일 경계·union 상위 3 정렬 검증.

## 재검토 조건
- 랭킹 차원이 늘거나(시간대별 등) Redis 메모리가 부담되면 → 집계 저장소·윈도우 전략 재검토.
