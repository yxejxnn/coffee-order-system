# adr — 아키텍처 의사결정 기록 (Architecture Decision Records)

**"왜 이 구조로 설계했는가"를 근거·대안과 함께 남기는 곳**이다.
코드는 *무엇을* 하는지 보여주지만, ADR은 *왜 그렇게 정했는지*(검토한 대안, 트레이드오프, 재검토 조건)를 보존한다.

> 채용/실전 과제에서 특히 중요하다: 대부분의 평가가 "정답"이 아니라 **"본인의 설계 논리를 설명·설득"**을 본다.
> 동시성·일관성·확장성처럼 **선택의 이유가 곧 점수**인 결정은 반드시 ADR로 남긴다.

## 언제 ADR을 쓰나

- 되돌리기 어렵거나 시스템 전반에 영향을 주는 **구조적 선택** (동시성 제어 방식, 트랜잭션 경계, 메시징 도입, 랭킹 집계 전략 등).
- **대안이 여럿이고 트레이드오프가 있는** 결정.
- 나중에 "왜 이렇게 했지?"라는 질문이 나올 만한 결정.
- (사소한 구현 디테일·일회성 선택은 ADR이 아니라 `design.md`나 로그에 남긴다.)

## 위치 & 이름

```
docs/adr/
├── README.md                 ← (이 문서)
├── ADR-template.md           ← 복사해서 새 ADR 작성
└── ADR-{번호}-{제목}.md       예: ADR-001-포인트-동시성-제어.md
```

- 번호는 **001부터 순차 채번**(누적, 재사용 안 함).
- 한 결정 = 한 파일. 완료 후에는 상태만 바꾸고 내용은 원칙적으로 고치지 않는다(대체 시 새 ADR로).

## 상태(Status) 규칙

- `Proposed` — 검토 중 (Clarify에서 나온 초안일 수 있음).
- `Accepted` — 채택. 구현이 이 결정을 따른다.
- `Superseded by ADR-00X` — 다른 결정으로 대체됨 (이유와 링크를 남긴다).
- `Deprecated` — 더 이상 유효하지 않음.

## 워크플로우 연결

- **Clarify/Plan 단계**에서 구조적 결정이 필요하면 planner가 **ADR 초안(`Proposed`)**을 만든다.
- 사용자(또는 튜터) 승인 후 `Accepted`로 바꾼다 → 이게 휴먼 게이트의 승인 대상에 포함된다.
- 각 기능의 `design.md`는 관련 ADR을 **링크로 참조**한다 (규칙을 복붙하지 않는다).
- 미결정이라 멈춘 질문은 `docs/open-questions.md`에 남기고, 결정되면 ADR로 승격한다.
