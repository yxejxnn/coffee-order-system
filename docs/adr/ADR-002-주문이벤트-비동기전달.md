# ADR-002 주문 완료 이벤트 비동기 전달 — Kafka (커밋 후 발행)

## 상태와 결정일
Accepted. 결정일: 2026-07-14.

## 맥락과 문제
주문/결제가 완료되면 두 가지 후속 작업이 필요하다.
1. 주문내역을 **데이터 수집 플랫폼으로 실시간 전송**(발제 3).
2. **인기 메뉴 카운트 증가**(발제 4). → [ADR-003](ADR-003-인기메뉴-집계전략.md)

이 후속 작업을 주문 트랜잭션 안에서 동기로 하면, 외부 전송 지연·실패가 주문 결제 자체를 지연/실패시킨다(결합도↑, 사용자 응답 느려짐). 멀티 인스턴스에서도 안전해야 한다.

## 결정 동인
- 주문 결제(핵심 경로)와 후속 처리(부가 경로)의 **결합 분리**.
- 후속 작업의 **재처리·확장성**(소비자 추가가 쉬움).
- "커밋 안 된 주문"이 전송/집계되면 안 됨(일관성).

## 검토한 선택지

| 선택지 | 결제 경로 영향 | 유실/중복 | 확장성 | 판단 |
| --- | --- | --- | --- | --- |
| **Kafka + 커밋 후 발행(`@TransactionalEventListener(AFTER_COMMIT)`)** | 없음(비동기) | 발행 실패 시 유실 가능 → 재시도+로그로 완화 | 소비자 그룹 추가로 확장 | **채택** |
| 동기 REST 직접 호출 | 있음(지연·실패 전파) | 트랜잭션과 원자적이지 않음 | 낮음 | 제외 |
| Outbox 패턴(릴레이 테이블) | 없음 | 유실 0에 가장 강함 | 높음 | **보류**(아래) |

## 결정과 이유
주문 트랜잭션 **커밋 후**(`@TransactionalEventListener(phase = AFTER_COMMIT)`) `OrderCompletedEvent`를 Kafka로 발행한다. 소비자는 **두 컨슈머 그룹**:
- (a) 데이터 수집 플랫폼 전송(Mock),
- (b) 인기 메뉴 Redis 카운트 증가.

커밋 후 발행이라 **커밋되지 않은 주문은 절대 전송/집계되지 않는다**. 발행 실패 시 N회 재시도 후 로그로 남긴다.

**Outbox 보류 사유**: 유실 0 보장에는 Outbox가 더 낫지만, 릴레이 구현·운영 부담이 있고 본인이 실습으로 체득해 인터뷰에서 방어할 수 있는 범위를 넘어선다. 과제에서는 **"고려했으나 범위상 제외"**로 남기고, at-least-once 전제 + 소비자 멱등으로 정확성을 확보한다. → [ADR-003](ADR-003-인기메뉴-집계전략.md)

## 결과와 단점
- 얻는 것: 결제 경로 경량·빠름, 소비자 독립 확장, 커밋-후-발행으로 유령 데이터 없음.
- 비용: 발행과 커밋이 원자적이지 않아 **드문 유실 가능**(재시도로 완화, Outbox 미도입 트레이드오프를 README에 명시). Kafka 운영 요소 추가.

## 검증 현황과 계획
- Level 5~6: 주문 → 이벤트 발행 → 두 소비자 처리(전송 Mock 호출 확인, Redis 카운트 증가 확인) 통합 검증.

## 재검토 조건
- 전송/집계 유실이 비즈니스상 허용 불가로 승격되면 → Outbox 도입.
