# Evaluate 가이드 (evaluate-guide)

실행 흐름의 **Evaluate(평가) 단계**에서 이 문서를 참고한다.
평가는 **두 가지를 모두** 수행한다: 계산적(자동) + 추론적(판단).

## 역할 경계 — Evaluate는 어디까지

Evaluate는 **실행 + 판정 + 실패 보고**까지다. 실패의 **원인분석·수정·해결책**은 넘지 않는다 (그건 Generate의 재시도 몫). Plan의 "고도 경계"와 대칭이다.

| ✅ Evaluate가 한다 | ❌ 넘지 말 것 (Generate 재시도 몫) |
|---|---|
| 대상 기능으로 **스코프한 테스트 실행** | 테스트 XML/HTML **심층 파싱**, jar `unzip` |
| **gradle 출력**으로 통과/실패 판정 | 프레임워크 내부 **포렌식 디버깅** |
| 계획·컨벤션·정책 준수 확인 | 실패의 **근본원인·해결책** 찾기 |
| 실패 **신호(gradle 메시지)**를 보고 + 로그 기록 | (원인분석·수정은 generator가 다음 시도에) |

> 테스트 실패 시: gradle이 뱉은 실패 메시지를 **그대로 보고**하고 끝낸다. 깊이 파헤치지 않는다 (python 파싱·unzip 등은 이 경계를 넘은 것).

## 1. 계산적 평가 (자동)

- **대상 기능으로 스코프**해 검증한다: `./gradlew test --tests "*{기능}*"` (전체 스위트 남발 금지). 필요 시 `compileJava`도.
- **DB 미가동 구분**: 테스트 실패가 로직 문제인지, DB 미가동/스키마 문제인지 구분해 보고한다.

### 검증 레벨 (Verification Level) — "어디까지 실제로 검증했나"

"테스트 통과"라는 문장만으로 완료를 주장하지 않는다. **어느 레벨까지 실제로 확인했는지**를 로그에 명시한다.
Mock 통과는 실제 DB·인프라·API 검증을 **대체하지 못한다** — 특히 동시성·데이터 일관성처럼 "실제로 돌려봐야 아는" 것은 해당 레벨을 반드시 밟는다.

| Level | 대상 |
| --- | --- |
| Level 0 | 문서·정적 검사·하네스 자체 |
| Level 1 | 빌드 + 단위 테스트 + 전체 회귀 smoke |
| Level 2 | Controller/API 계약 (요청·응답·검증·에러) |
| Level 3 | DB·트랜잭션·JPA·**락·동시성** 통합 |
| Level 4 | 외부 인프라 통합 (메시징·캐시 등, 해당 시) |
| Level 5 | 로컬 애플리케이션 기동 |
| Level 6 | 실제 HTTP 요청 (curl·Postman·`.http`) |
| (Level 7) | 부하/스트레스 관찰 (필요 시, 선택) |

- **기록 규칙**: 통과한 레벨과 그 근거(명령·결과·API 샘플)를 `docs/logs/`에 남긴다. 결과값은 `PASS`/`FAIL`/`PARTIAL`, **완료 근거에는 `PASS`만** 쓴다.
- API 동작·런타임·인프라가 바뀌면 Level 5·6 필요 여부를 Plan에서 미리 결정한다(기본값 필요=YES). 문서·운영만 바뀌면 낮은 레벨로 한정할 수 있다.

## 2. 추론적 평가 (판단)

- 결과물이 **승인된 계획대로**인지 확인한다.
- **코드 규칙**(`docs/code-convention.md`)을 지켰는지 확인한다.
- 관련 **정책**(`docs/policy/`)을 위반하지 않았는지 확인한다.

## 보고 & 기록

- 결과(통과/실패, 실패 시 원인)를 **사실대로** 보고한다. 통과하지 않았으면 "통과"라고 말하지 않는다.
- **성공이든 실패든**, generator가 남긴 `시도`에 이어 **`결과`·`원인`·`증거`(API 샘플)를 `docs/logs/`에 append**한다. 방법: `docs/logs-guide.md`.

## 통과 시 후속 (Push → PR → 자체 리뷰 → merge)

Evaluate를 통과하면 바로 "완료"가 아니다:
1. feature 브랜치를 **push하고 PR을 연다**(base: `dev`, `Closes #N`). 세부: `docs/workflow/issue-pr-guide.md`.
2. **Claude가 PR을 자체 리뷰(/code-review)→수정**을 통과까지 돌린 뒤, **머지 직전에 멈춰** 사람의 최종 검토를 기다린다. **merge는 사람만.**
3. 사람이 **merge한 뒤**에 (`docs/dev-doc-guide.md`):
   - 대상 기능의 **`design.md`를 최종 상태로 갱신**(SSOT).
   - ongoing 문서를 해당 기능 **`changes/00X`로 채번 이동**.
   - 사용한 **feature 브랜치를 삭제**(로컬+원격).

## 실패 시 (루프 규칙 — 원천)

Evaluate(또는 PR 리뷰 코멘트)가 통과하지 못하면:

- **같은 접근으로 고칠 수 있는 실패** → Generate로 돌아가 구현만 다시 한다 (재승인 불필요).
- **접근 자체를 바꿔야 하는 실패** → Plan으로 돌아가 **새 계획을 승인(게이트 A)**받은 뒤 진행한다.
- **무한 반복 방지**: 같은 방식으로 **3회 연속 실패**하면 멈추고 사용자에게 상황을 보고한다.
