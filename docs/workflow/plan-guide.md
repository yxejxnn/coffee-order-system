# Plan 가이드 (plan-guide)

실행 흐름의 **Plan(계획) 단계**에서 이 문서를 참고한다.
Plan의 목표: 코드를 만들기 전에 **무엇을·어떻게·어떻게 검증할지**를 문서로 확정하고 사람의 승인을 받는 것.

## Clarify 먼저 — 애매하면 멈춘다

계획을 세우기 전에, 요구사항·정책에 **공백이나 모호함**이 없는지 본다.

- 비어 있거나 여러 해석이 가능하면 → **`docs/open-questions.md`에 질문을 남기고 멈춘다.** 추측으로 메우지 않는다.
- 그 결정이 **구조적**(동시성·트랜잭션 경계·메시징·확장성 등)이면 → **`docs/adr/`에 ADR 초안(`Proposed`)**을 만들어 대안·트레이드오프를 정리하고 승인을 받는다.
- 이 관문을 건너뛰고 "적당히 추상적으로" 진행하지 않는다. (하네스의 존재 이유)

## 계획 전에 먼저 읽고 확인할 것

- **`docs/agent-mistakes.md`** — 과거 반복 실수를 확인해 같은 함정을 피한다.
- **관련 `design.md`** — 대상 개념/기능의 현재 상태를 파악한다 (`docs/dev/{개념}/{기능}/design.md`).
- **관련 정책·ADR** — 이 작업이 걸리는 비즈니스 규칙(`docs/policy/`)과 이미 내려진 결정(`docs/adr/`)을 확인한다.
- **`docs/dev/ongoing/`** — 진행 중인 작업과 **중복·충돌**이 없는지 본다.
- **영향 범위** — 바뀔 파일/계층(controller·service·repository·entity·dto)을 식별한다.

## 계획에 담을 것

- **무엇을**: 변경 대상 (기능·파일·영역)
- **어떻게**: **접근/설계 방향**만 (필요하면 정책 참조). ⚠️ 구현 메커니즘이 아니다 — 아래 "고도(altitude) 경계" 참고.
- **통과(평가) 기준**: 어떤 테스트/확인으로 완료를 판정할지, **필요 검증 레벨**(특히 Level 5 로컬 기동·Level 6 실제 HTTP 필요 여부)을 미리 정한다 (레벨 표: `docs/workflow/evaluate-guide.md`)
- **리스크/전제**: DB 가동 필요 등 전제·리스크 해당 여부

## 고도(altitude) 경계 — Plan은 어디까지 정하나

Plan은 코드를 **읽어도** 되지만(영향 범위·리스크 파악용), 코드레벨을 **규정하지는 않는다**.
구체 구현은 Generate의 몫이다. 이 선을 넘으면 Plan/Generate 경계가 무너지고, Bash 없는 planner가
검증 못 하는 것을 처방하게 된다.

| Plan이 정한다 (✅) | Generate가 정한다 (❌ Plan에 쓰지 말 것) |
|---|---|
| API/DB **계약**(`docs/api/`·`docs/db/`) | 애노테이션·라이브러리 API 선택 (`@NotBlank`, `@Valid` 등) |
| 영향 **계층** 목록 (controller·service·…) | 계층 **내부** 구현 배치 (어느 검증을 DTO/service 어디에 둘지) |
| **접근/설계 방향** ("제목은 Bean Validation으로") | 구체 **설정값**·의존성 처방 (`ddl-auto=update`, gradle 의존성 추가) |
| 통과(평가) 기준 | 클래스 내부 로직·정확한 문자열/코드값 |
| **리스크·전제**(사실만 기술) | 그 리스크의 **해결책**(해결은 Generate가 결정) |

- 전제는 **리스크로 "알리는" 데서 멈춘다**. 예: "Bean Validation을 쓰려면 의존성이 필요할 수 있다(현재 build.gradle에 없음)" ✅
  → "build.gradle에 `spring-boot-starter-validation`을 추가하라" ❌ (해결책 처방 = Generate)

## 이슈 쪼개기 (계획 단계에 한꺼번에)

작업을 **잘게 쪼개 이슈로** 만든다 — 그때그때 하나씩이 아니라, 계획 단계에 **전체를 한꺼번에**. 이 쪼갬(로드맵)을 사람이 게이트에서 먼저 검토해, "빠진 조각·순서 오류"를 개발 전에 잡는다.

- **잘게**: 이슈 하나 = 한 가지 일. 잘게 쪼갤수록 각 이슈에 숨은 구현(HOW)이 작아져, 미리 상세히 써도 안전하다.
- **WHAT은 미리 상세히**: 각 이슈의 목표·완료(평가)조건·영향범위·검증레벨을 이슈 본문에 상세히 적는다. (이건 안 썩는다 = 위 "고도 경계"에서 Plan이 정하는 몫)
- **HOW는 집을 때**: 애노테이션·내부배치·설정값 등 구현 세부는 그 이슈를 집을 때 정한다. 특히 **여러 이슈가 공유하는 구현 결정(엔티티 구조·공통 서비스)은 미리 박지 않는다** — 순서상 먼저인 이슈에서 확정되기 때문. 미리 복사해두면 앞 이슈 결과에 따라 뒤 이슈가 전부 stale 된다.
- **목록은 지도지 계약이 아니다**: 앞 이슈 개발이 뒤 이슈를 무효화하면 그 이슈를 수정/close한다.

> 한 줄: **잘게 쪼갠다. "무엇을·완료조건"은 미리 상세히, "어떻게"는 집을 때 — 공유 구현은 미리 박지 않는다.**

## 원칙

- **애매하면 추측하지 말고 사용자에게 질문**한다. 빈틈 있는 계획으로 넘어가지 않는다.
- 계획 범위를 벗어나는 작업을 임의로 넓히지 않는다.
- 계획 없이 바로 코드를 생성하지 않는다.

## Plan의 산출물

- **전체를 잘게 쪼개 GitHub Issue로** 만든다(`gh issue create`) — 계획 단계에 한꺼번에. 각 이슈 본문엔 WHAT(목표·완료조건·영향범위)을 상세히, HOW는 비운다. 발급된 `#N`을 개발문서에 연결한다. (쪼개기 원칙: 위 "이슈 쪼개기" · 방법: `docs/workflow/issue-pr-guide.md`)
- 각 이슈에 **완료 체크리스트의 해당 항목 + 검증 레벨 결정(Level 5/6 필요 여부·이유)**을 함께 기재한다 — PR이 이걸 복사한다. (`docs/workflow/issue-completion-checklist.md`)
- Plan은 **`docs/dev/ongoing/{작업}.md`** 개발문서를 만드는 것으로 이어진다 (`이슈: #N` 필드 포함). 각 이슈의 상세 설계(HOW)는 그 이슈를 집을 때 채운다.
  (문서 작성법·필드·템플릿은 `docs/dev-doc-guide.md` 참고)
- 필요하면 **API 명세(`docs/api/`)·테이블 명세(`docs/db/`)도 이 단계에서 작성**한다.
  (generator는 이 명세대로 코드만 구현한다.)
- 구조적 결정이 있으면 **ADR(`docs/adr/`)**을, 미결정 질문이 있으면 **`docs/open-questions.md`** 항목을 함께 만든다.
- 위 문서들이 곧 **휴먼 게이트에서 승인받을 대상**이다 (계획 + 명세 + ADR).

## 승인 후 (모드별)

- **기본 모드**: 승인되면 Generate로 넘어간다. 승인 전에는 파일을 수정/생성하지 않는다. (Claude Code는 Plan Mode로 이 관문을 강제)
- **자율 모드** (`plan-generate-evaluate-loop` 워크플로우): 휴먼 게이트를 생략하고 Plan 완성 후 바로 Generate로 이어진다. 통제는 사후 검토·테스트·루프 상한으로 대체. → 상세: `docs/branch-guide.md` "실행 모드".
